### D-data-1: One canonical code style for corpus, prompts and tasks (2026-11-13)
- Decision: every piece of Python the model sees is passed through `lsllm.canon.canon` (`ast.unparse` formatting, 4-space indentation, no comments, no blank lines outside docstrings, docstrings dedented, ASCII only). Benchmark prompts (HumanEval, MBPP, custom) are canonicalised the same way.
- Why: a model of a few hundred thousand parameters cannot afford to spend capacity on formatting variety (the TinyStories lesson: small models need a narrow, regular distribution). Canonicalising a prompt changes layout only, never the task.
- Numbers: none yet; the token saving is measured by the tokenizer area.
- Rejected: training on raw formatting (more entropy per token, more tokens per function).

### D-data-2: Indentation and newlines as structure tokens, one token per line break (2026-11-13)
- Decision: marker text before SentencePiece: `<NL>` (same level), `<IND>` (level + 1), `<DED1>`..`<DED5>` (level - k), `<LF>` (newline inside a docstring). Leading spaces never appear as tokens.
- Why: the brief asks to keep indentation and newlines as tokens. Level-change tokens cost exactly one token per line break at any depth (literal indentation costs one token per level per line), which shortens sequences (fewer tokens per function = more functions per second and more code per 256-token context) and makes the indentation rule of the syntax filter a table lookup.
- Rejected: literal 4-space tokens (longer sequences); raw text with SentencePiece defaults (SentencePiece collapses whitespace and drops newlines).

### D-bench-1: What "overlap with a benchmark" means, and the two strata of the custom set (2026-11-13)
- Decision: a training function overlaps a benchmark if (a) its name equals a benchmark entry point, or (b) its `alpha_key` (code fingerprint that ignores names and docstrings) equals that of a reference solution, or (c) its docstring equals a prompt docstring. Such functions are removed from the corpus and never generated synthetically. The custom-200 set has two strata: "near" (120 tasks; the family may appear in synthetic training data, the task itself may not) and "far" (80 tasks; the whole family is absent from synthetic data). Scores are reported per stratum and in total.
- Why: for one-line tasks ("add two numbers") semantically equal code exists everywhere, so "never seen" has to be defined precisely to be defensible. Two strata separate "learned the family" from "generalises to unseen families".
- Rejected: only exact-text deduplication (too weak for trivial functions); removing every semantically similar function (undecidable, and would remove the basics the model must learn).

### D-bench-2: Metrics and prompt formats (2026-11-13)
- Decision: HumanEval uses its own prompts (canonicalised). MBPP uses function-stub prompts in MultiPL-E style (signature from the reference solution, task text as docstring), test split = task ids 11-510, practice = 511-974. Per sample the outcome is pass / wrong / error / timeout / syntax; ladder metrics are `syntax_ok` (parses) and `runs_ok` (pass or wrong: executed without an exception). pass@1 is reported greedy (what the FPGA does without sampling) and sampled; pass@10 uses the unbiased estimator of Chen et al. (2021) from 10 samples.
- Why: one prompt style across benchmarks matches what the model is trained on; the stub form gives the model the function name and arity, which a docstring-only prompt would hide (stated openly as a deviation from the original MBPP text-only prompt).
- Rejected: MBPP text-plus-asserts prompts (a different input format the tiny model never sees in training).

### D-ls-cpu-1: One instruction table drives encoder, decoder, assembler and simulator (2026-11-13)
- Decision: `lsllm/ls/isa.py` holds one table, `INSNS`, with one row per mnemonic: opcode, format, fixed fields (function code), operand fields, cycle cost, effect function. `encode`, `decode`, the assembler (`asm.py`) and the simulator (`iss.py`) all read it. A new instruction is one effect function plus one row (a new operand notation also needs one entry in `asm.KIND`, a new format one entry in `isa.FORMATS`). The decoder accepts exactly the words the encoder can produce.
- Why: the brief asks that adding an instruction stays local; with one table the assembler and the simulator cannot disagree about an encoding, and a corrupted word is refused when the program is loaded instead of being executed.
- Numbers: 28 mnemonics on 16 opcodes and 6 formats; 26,255 of the 65,536 words are instructions (counted by hand from the formats, confirmed by a test over all words); the nine encoding examples of the design document are reproduced (0x8040, 0x8000, 0x14C0, 0x2102, 0x3400, 0x4700, 0x7B01, 0x9202, 0xF009).
- Rejected: separate tables for encodings and effects (two places to edit); a decoder that ignores reserved bits.

### D-ls-cpu-2: The simulator executes whole instructions and charges cycles from the table (2026-11-13)
- Decision: `LS.step()` applies the complete effect of one instruction and adds its cost: 4 cycles for every instruction (HALT included), n + 4 for `MAC #n` (so 5 for `MAC #1`). `MAC #n` is executed as n classic MACs. The read registers XR/WR, the valid bits V1/V2, the counter CNT, the clock enable and the run modes are not modelled.
- Why: the design document states that timing does not depend on data, that the one-cycle read latency is invisible to ordinary instructions, and that `MAC #n` has exactly the architectural effect of n classic MACs. This was checked, not assumed: `tests/test_ls_stream.py` contains a second, clock-by-clock model written from the state table and the STREAM contract of 06-control.tex; it reproduces the MAC #4 table of the document and agrees with the simulator for every n = 1..255 (ACC, PROD, pointer, n + 4 cycles, with stale values in XR/WR at the start).
- Numbers: S/U/L/B give 112/300/560/1,328 cycles on the 64-input neuron and 80/172/304/688 on the 32-input neuron; instructions 12/75/140/332 at N = 64; words 12/75/14/17 (U: 43 at N = 32). All equal the predictions of numbers.tex. 96 random data sets and 60 worst-case sets (operands -128/127, bias -32768/32767, shifts 0..23, ReLU on/off) give the exact integer dot product and the output byte of a numpy reference, with the overflow flag clear. Simulator speed, CPU time on the M1 while other agents loaded the machine: about 1.1 M ordinary instructions/s and 1.7 M stream elements/s (a 1 M-cycle program takes roughly half a second).
- Rejected: a clock-accurate simulator (only clock-enable pauses and cycle-stepping need it, and no program can observe them); numpy inside the stream (pointer wrap-around and the exact overflow flag are simpler one element at a time).

### D-ls-cpu-3: Readings chosen where the design document is silent or ambiguous (2026-11-13)
- Decision: what the document leaves open, and the reading implemented in `lsllm/ls`:
  1. Register field of `IN Rd` and `OUT Rs` (format R has r1 and r2): r1, bits 11..10, where formats I, M and Q also keep their single register.
  2. Unused fields (r2 of IN, OUT and the shifts; r1, r2 of NOP, HALT, ADDP; fn of MUL): written as 0. The decoder refuses any other value, a reserved bit that is 1, and undefined function codes (SYS fn > 3, ALU fn > 8, MVP fn > 1, opcode 7 fn > 1, MUL fn > 0).
  3. Shifts take one operand (`SHL Rd`). SHL and SHR shift in a 0, SAR keeps bit 7; the bit shifted out is lost (there is no carry flag).
  4. Flags: only the nine ALU instructions (MOV included) write Z and N. The rows of LDI, IN, LD and RQ do not mention flags (DJNZ says "flags unchanged"), so they leave them.
  5. `RQ`: sh is limited to 0..23 (figures/rq.tex) although the field has 5 bits. The third operand is required and is a number or name with value 0 or 1; the lowercase name `relu` is predefined as 1 (encoding example `RQ R0, 2, relu`), the `RELU` of the listing is an ordinary named constant.
  6. Open decisions of the document are implemented as it is written today: RQ rounds toward minus infinity; `MAC #1` streams (5 cycles) and `MAC #0` is the classic MAC; `ST` exists and writes X through P0 only (`ST Rs, [P1]` is refused); there is no branch on N; ACC wraps in 24 bits. The sticky overflow flag exists only in the simulator (`LS.overflow`); a program cannot read it.
  7. Reset values are not given: registers, flags, pointers, PROD, ACC and OUTR start at 0, PC at 0. The 8-entry start table (several programs in one ROM) is not modelled; a program is assembled at address 0.
  8. Program ROM: the document has 256 words addressed by PC[7:0]. The simulator takes up to 4,096 words (12-bit PC) and stops with an error when PC leaves the program, instead of wrapping inside 256 words.
  9. Memory address: X and W see the low bits of their pointer (P[7:0] for 256 cells). With the size as a parameter this is pointer mod size, the size being a power of two. Pointers and PC wrap at 12 bits.
  10. `DJNZ` with R3 = 0: R3 - 1 wraps to 255 and the branch is taken (256 passes).
  11. PROD after a stream is its last product (table of 06-control.tex), so an `ADDP` after `MAC #n` adds that product again. PROD only changes in MUL, MAC and MAC #n.
  12. Assembler syntax that the listings do not show: `NAME = value` defines a constant; `.region name` marks a region; numbers are decimal, 0x or 0b; the MAC count needs `#`; immediates are written 0..255 (no negative literals); mnemonics and registers in capitals, names case-sensitive.
  13. Inconsistency: the title page and numbers.tex say "spec v0.1", the open-decisions box of 05-isa.tex says "spec v0.2". The listings of 07-programs.tex reproduce every count of numbers.tex, so nothing had to be chosen.
- Why: the brief forbids guessing silently; each reading is the one that follows most directly from the nearest statement in the document, and the strict ones (2, 5, 8) turn an undefined case into an error instead of a silent result.
- Numbers: none of the readings changes a word or a cycle of S, U, L, B (they use R0 for IN and OUT, and no undefined case).
- Rejected: accepting undefined encodings and inventing a behaviour for them; a two-operand `RQ Rd, sh` (not in the document).

### D-ls-cpu-4: Regions are address ranges marked in the assembly text (2026-11-13)
- Decision: a line `.region name` tags the instructions that follow, up to the next mark. The simulator charges the cycles of every executed instruction to the region its address lies in (`LS.region_cycles`), next to cycles per mnemonic (`LS.insn_cycles`), `LS.cycles` and `LS.instructions`. Code before the first mark is charged to `None`. `LS(words, regions={address: name})` accepts the same marks without the assembler.
- Why: a program generator writes a mark where it starts emitting a part of the model. A tag that depends only on the address does not depend on the path taken, so it stays correct with loops and jumps, and it costs no cycles.
- Numbers: S64 splits into prologue 32, body 68, epilogue 12 cycles; the bodies of U64, L64, B64 are 256, 516 and 1,284 cycles.
- Rejected: marker instructions (they would cost cycles or need an opcode the hardware does not have); using labels as regions (a loop label would cut a part in two).

### D-bench-3: The sandbox: deny-by-default profile, base interpreter, private directory (2026-11-13)
- Decision: `lsllm.sandbox.run_python` runs each program in a fresh base CPython (`-I -S`, the interpreter behind the virtualenv symlink) under `sandbox-exec` with a profile that starts with `(deny default)` and allows only: exec of that one interpreter, `sysctl-read`, reading `/`, `/usr`, `/System`, `/dev/null`, `/dev/urandom`, the interpreter installation and a private temporary directory created for the run, and writing that directory and `/dev/null`. The environment is not passed on (only `TMPDIR`), stdin is empty, the directory is deleted afterwards.
- Why: with deny-by-default anything we did not think of is refused (sockets, fork, exec of other programs, Mach services, the rest of the file system). `-I -S` with the base interpreter hides site-packages, so only the standard library can be imported.
- Numbers: 15 tests in `tests/test_sandbox_denials.py`, one per denial (network connect/bind/urllib with a control connection outside the sandbox, writes to home, project and temp, reads of home and `/etc/passwd`, fork/subprocess/posix_spawn/exec/os.system, signalling the parent, environment, loop, sleep, memory, output, disk). Start-up cost per layer over 100 starts: interpreter 20.3 ms, with sandbox-exec 25.8 ms, with the limit prelude 29.1 ms, whole `run_python` 34.4 ms. Inside the sandbox local time is UTC and named time zones are missing (`/var/db/timezone` is not readable).
- Rejected: an allow-by-default profile with a list of denials (whatever is forgotten is allowed); running the virtualenv interpreter (numpy and torch importable); passing the environment (it can hold secrets).

### D-bench-4: Memory limit by a watchdog on the memory footprint, not by rlimit (2026-11-13)
- Decision: the parent polls the child every 10 ms with `proc_pid_rusage` and kills its process group when `ri_phys_footprint` exceeds the limit (default 512 MB; 128 MB per sample in `evaluate`, where four run at once).
- Why: `setrlimit(RLIMIT_AS | RLIMIT_DATA | RLIMIT_RSS, 512 MB)` is refused on this macOS (`ValueError: current limit exceeds maximum limit`): a fresh interpreter already has 466.2 GB of virtual address space. The footprint counts compressed pages; the resident size does not (seen: resident 413 MB while the footprint was 734 MB).
- Numbers: a program allocating 2 GB was killed after 0.057-0.060 s with a peak of 124-133 MB at a 100 MB limit, and after 0.108-0.119 s with a peak of 530-602 MB at 512 MB. Swap in use was 2616.19 MB before and after seven such runs. Largest footprint of a reference solution: 11 MB (HumanEval), 8 MB (MBPP).
- Rejected: `RLIMIT_AS` set to the child's own virtual size plus 512 MB (it is accepted and enforced, a 2 GB allocation then raises MemoryError, but it has to be set by code running inside the untrusted interpreter and it limits address space, not memory); polling with `ps` (one process per poll).

### D-bench-5: Limits that hold when the parent dies, and a cap on disk writes (2026-11-13)
- Decision: a one-line bash prelude sets two kernel limits before it execs sandbox-exec: CPU time `int(timeout) + 2` seconds and 8 MB per file. The child is started in its own session and the wall-clock timeout kills its process group. Stdout and stderr go to files in the private directory; the first 64 KB of each are returned. The watchdog also kills a run that has written more than 8 MB in total (status `error`, with a line in stderr).
- Why: the parent can be killed (10-minute command cap, `tools/guard.sh` uses `pkill -9`); then only the kernel stops a child that spins. Disk is the scarcest resource of this machine (it fell below 200 MB free today).
- Numbers: a 1 s CPU limit ended a spinning interpreter with SIGXCPU after 1.41 s; a 1 MiB file limit stopped a write at exactly 1,048,576 bytes. After `kill -9` of a parent with four spinning children (timeout 3 s, so 5 CPU seconds) all four were gone 16.5 s later on the loaded machine. After Ctrl-C the parent returned once the runs in flight had ended (at most one timeout) and no child was left. An endless `print` loop ended after 0.075 s, endless file creation after 0.058 s.
- Rejected: `preexec_fn` to set limits (documented as unsafe with threads, and `run_many` uses threads); pipes for the output (need reader threads to drain them). Not covered: a child that sleeps forever after its parent was killed stays until it is killed by hand (it uses no CPU); private directories of runs whose parent was killed stay in the system temp folder (a few KB each).

### D-bench-6: How the tasks are built, and which reference solutions cannot pass (2026-11-13)
- Decision: HumanEval prompt = `canon(prompt)`, tests = the dataset's test code plus `check(entry_point)` as one block. MBPP prompt = signature of the function that the first assert calls (from the reference code) with the task text as docstring; tests = `test_setup_code` (two tasks have one) and each assert. For the harness self-check the MBPP reference is put into the same shape: its imports, helper functions and constants move into the function body (module-level assignments to names that are parameters are left out; this matters for tasks 607 and 631). No task is dropped; the loaders raise if a task cannot be built.
- Numbers: eight non-ASCII characters are replaced so that `canon` accepts the text. HumanEval, 10 prompts: the arrow U+279E becomes `->` in 72, 74, 92, 125, 126, 132, 134, 137; U+2264 becomes `<=` in 84, 147. MBPP, 9 task texts: U+2019 and U+2018 become `'` (122, 207, 360, 645, 679, 767), U+2013 becomes `-` (260), U+2026 becomes `...` and U+00B3, U+00B2 become `^3`, `^2` (931, 935). All 974 MBPP references parse under Python 3.12 and in all of them the three asserts call a function the reference defines; 740 references are one function, 234 have other module-level statements (146 import, 47 from-import, 46 helper functions, 16 assignments, 4 classes). Two pairs of MBPP tasks have identical prompts (76 and 347, 248 and 704); either reference passes both tasks of its pair.
- Numbers, reference solutions through the full harness (seven runs with a 30 s timeout, identical every time): HumanEval 164/164, MBPP test 497/500, MBPP practice 461/464. The six that fail: 180 and 493 compare floats with `==` and this platform's sin/cos/acos/tan differ from the expected values by one unit in the last place (they also fail as unmodified module-level code); 367, 927 (class `Node`), 601 (class `Pair`) and 596 (`sys`) have tests that use a name only the reference code defines at module level, which a function body cannot provide. They stay in the denominators, so a score on our MBPP test split is at most 497/500 here. Task 123's reference needs 3.3-3.5 CPU seconds (6.6-11.5 s wall on the loaded machine), so it can exceed the default 5 s timeout: the same check at 5 s under load gave 496/500.
- Rejected: dropping the six tasks (the splits would no longer be the 500 and 464 tasks of the paper); putting the reference's imports, helpers and classes into the prompt (gives away part of the solution in 234 tasks); comparing floats with a tolerance (changes the benchmark's tests).

### D-bench-7: Scoring rules of `evaluate`, and what is recorded (2026-11-13)
- Decision: one program = prompt + continuation, cut at the first line that starts in column 0. Syntax is checked with `ast.parse` in the parent. A driver inside the sandbox defines the candidate, runs every test statement on its own and prints one report line that starts with a random token made for this evaluation; what the candidate prints is discarded. Outcome: `syntax`; `timeout` (5 s wall-clock for the whole sample); `error` if the definition or any test raised, or the run was killed or gave no report; else `wrong` if any assert failed; else `pass`. Task number g is sampled with `seed + g`. `evaluate` returns a `Report` and writes nothing; `lsllm.bench.results.record(report, ...)` (the CLI flag `--record`) appends the line to `results/results.jsonl`, saves the per-sample records as `results/samples/*.jsonl.gz` and renders `RESULTS.md`. The benchmark and split names travel with the tasks (`task.meta`), and every row whose split is not `test` goes to the practice table.
- Why: an exception outranks a failed assert so that `runs_ok` means "nothing raised". The random token means a program cannot print itself a pass. Not recording by default keeps harness checks and smoke runs out of the results table (INTERFACES section 7 says every evaluation appends a line; this is the one place where the code differs from that wording).
- Numbers: HumanEval's own harness uses a 3 s timeout; ours is 5 s because wall-clock time on this shared machine was 2 to 3.5 times CPU time during the measurements.
- Rejected: counting a `SyntaxError` that only the compiler finds (for example a duplicate argument name) as `syntax` (the rule "parses" would need a second definition; such a sample is an `error`); recording every call (see above).

### D-bench-8: Validation of the harness before any model is scored (2026-11-13)

A sample parses when the random text happens to end the function at once, for example a newline followed by a character in column 0.
- Numbers, throughput with 4 workers (the machine was shared with training runs; load average in brackets): a program that does nothing 68 samples/s (moderate load, not noted), 59/s (18-29), 43/s (about 220); 109/s with 8 workers (18-29). HumanEval reference programs with their tests 44/s, median 0.083 s per sample (18-29); MBPP test references 29/s, median 0.120 s. Whole evaluations from the command line: HumanEval `empty` 164 samples in 3.1 s, MBPP test `empty` 500 in 9.9 s.
- Not done: no run with a trained model. `TorchCompleter("runs/q1/v0_base/ckpt.pt")` could not be constructed (`lsllm.tok.Tok` rejects `data/tok/q512/tok.model`), so the path checkpoint -> completer -> harness is untested and `torch` is not in the completer registry.

### D-tasks-1: Custom test set: 40 families of 5 tasks, 24 near and 16 far (2026-11-13)
- Decision: `data/bench/custom_test.jsonl` holds 200 tasks in 24 near families (ids 000-119) and 16 far families (ids 120-199), 5 tasks per family. `data/bench/custom_families.json` gives every family its stratum and its scope. Near = the most basic kinds: arithmetic on one, two or three numbers, comparisons, min/max of a few numbers, parity and sign, unit conversion, one if/else, boolean logic, range loops, building lists, aggregates, filters, maps, indexing, slicing, list predicates, list edits, string case and length, string predicates, counting characters, string indexing, string building, reversing. Far = gcd and primes, palindromes and anagrams, classification words, dictionaries, sorting, nested lists, words, running totals, digits, searching, duplicates, two lists, sequences, character transforms, rearranging, binary. Rule for synthetic data: a function that fits a far family counts as far, even when the wording of a near family fits it too (a list of divisors is a comprehension over a range but belongs to gcd_primes; the tens digit is one arithmetic expression but belongs to digits).
- Why: every family weighs the same; 5 test tasks leave room for 5 practice tasks and for synthetic variants of the same family; without the far-wins rule a generator for a near family could produce a far task by accident.
- Numbers: 200 tasks, 967 tests (4 to 6 per task; near 573, far 394). The reference body is 1 line in 165 tasks (near 110, far 55) and never more than 6 lines. Prompts have 43-184 characters (mean 118; near 106, far 137), prompt plus reference solution 61-283 characters (mean 159). Estimate with the two interim 512-token SentencePiece models of 13 November (`data/tok/m512`, `data/tok/q512`, not the final tokenizer): a prompt is 46-50 tokens on average and at most 79, prompt plus reference solution at most 128, the reference body at most 54.
- Rejected: fewer and larger families (one weak family would dominate a stratum); docstrings with examples as in HumanEval (they cost context that a 256-token model does not have).

### D-tasks-2: Tasks are written as plain Python and built into JSON lines (2026-11-13)
- Decision: the task sources are `lsllm/bench/custom/tasks_<split>/*.py`: a line `family = "..."`, then per task one function with a one-line docstring followed by its `assert` lines. `build.py` parses these files with `ast` (they are never imported), makes the text canonical with `lsllm.canon`, takes the def line and the docstring as the prompt and numbers the tasks in the order of the families file. `check.py` verifies the built files (its docstring lists the checks). `tests/test_custom_tasks.py` runs the checker, compares the built files with their sources and feeds the checker broken tasks.
- Why: a task stays readable and fixable as ordinary code, a source file can be run directly to try its asserts, and there is one source of truth for the JSON lines.
- Numbers: 1,963 lines of task sources in 6 files, `build.py` 60 lines, `check.py` 172 lines. The checker needs about 5 s for the test split (200 reference solutions, each in its own Python process with a 10 s limit, four at a time).
- Rejected: hand-written JSON (escapes, hard to read); importing the task modules or a decorator registry (more machinery than parsing); an id stored with each task (ids are positional, so the test sources are frozen from here on: inserting a task would shift the ids behind it).

### D-tasks-3: What a docstring must say and how the tests are written (2026-11-13)
- Decision: every docstring is one line "Return ... .". (1) Limits on the input are part of the docstring ("which is not empty", "where n is not negative") and the tests stay inside them. (2) When a test passes an empty list, string or dictionary, the docstring names the result unless the rule gives it without any convention (a count is 0, a filtered, mapped or reversed sequence is empty, "at least one" is False); sums (0), "all" (True) and inputs that stay empty are stated. (3) Ties and order are either excluded ("all different", "exactly one word is the longest") or defined ("first appears", "in the order they have in a"). (4) An index is introduced as "counting from 0". (5) Float results are tested only with values that are exact in binary and equal for the usual ways to write the formula (Celsius to Fahrenheit passes with `9 / 5` and with `1.8`). (6) Predicates are tested with `== True` and `== False`.
- Why: the quality bar is that a careful reader of the docstring alone can write a solution that passes; each item removes one kind of hidden convention. `== True` accepts 1 for True, so a logically right answer of another type is not failed.
- Numbers: 91 tasks have a test with an empty list, string or dictionary (94 tests); 17 of them state the result, in the other 74 the rule gives it. 36 tasks are predicates (188 tests with `== True` or `== False`).
- Rejected: `is True` (fails `a * b` as an answer to "both true"); empty-input tests without a stated result where a convention is needed (maximum, mean, first item: these docstrings exclude the empty input instead).

### D-model-1: The float model is llama2.c `model.py` with the attention written out (2026-11-13)
- Decision: `lsllm/model/llama.py` keeps upstream's parameter names, initialisation, RMSNorm, RoPE, grouped-query attention, SwiGLU, tied embeddings and no biases. - Numbers: default shape = 260,032 parameters. ### D-model-3: How the shape options are defined (2026-11-13)
- Decision: `tied_embeddings=False`: separate input and output matrices. `ffn="relu"`: `w2(relu(w1 x))`, `hidden_dim` as given. `norm="dyt"`: `weight * tanh(alpha * x)`, one learnable scalar `alpha` per norm layer started at 0.5 (the paper's default), plus one learnable scalar after the embedding started at sqrt(dim). `attn="sigmoid"`: `sigmoid(score + b)`, one learnable `b` per layer started at -log(max_seq_len). `window=W`: a position attends to itself and the W - 1 positions before it.
- Why: the embedding scalar is in the DyT paper's Llama recipe (its appendix: without it "the training struggles to progress"); the window counts the current position because `ModelConfig.kv_cache_bytes` sizes the cache as W positions.
- Numbers: `ModelConfig.n_params()` does not count these scalars: DyT adds 2 * n_layers + 2, sigmoid adds n_layers (12 and 5 for the default depth). Tests: shapes, finite gradients, and for every option that changing a later token leaves all earlier logits bit-identical; with a window, a change at position p reaches exactly n_layers * (W - 1) positions further.
- Not verified: that DyT or sigmoid attention train as well as the baseline on real data. The only evidence is a toy stream (all options together: validation loss 0.11 after 60 steps).

### D-model-4: The training run (2026-11-13)
- Decision: `lsllm.train.run` uses the stories260K recipe of llama2.c where it applies: AdamW betas (0.9, 0.99), weight decay 0.01 on matrices only, gradient clipping at 1.0, linear warm-up then cosine decay to zero, peak learning rate 1e-3. Defaults of ours: batch 64, dropout 0 (upstream 0.05), warm-up 5% of the steps and at most 1000 (upstream 1000 of 100,000). Validation: the same evenly spaced, non-overlapping windows of `val.bin` for every run with the same context length (512 windows or all that exist). `ckpt.pt` holds the weights with the lowest validation loss. `--init-from` takes shape and weights from a checkpoint and starts a new schedule; the stored step count adds up. Distillation: `(1 - a) * CE + a * t^2 * KL(teacher || student)` at temperature t.
- Why: fixed windows make runs comparable pair by pair; upstream draws new random batches at every evaluation.
- Numbers: upstream command (`doc/stories260K.md`): batch 128, context 512, lr 1e-3, dropout 0.05, weight decay 0.01, beta2 0.99, 100,000 steps, warm-up 1000; reported validation loss 1.2968 on TinyStories. A smoke run, not a trained model.
- Caveat: the reported validation loss is the minimum over the evaluations of a run, on the windows it is reported on.

### D-model-5: The completer keeps prompt and answer inside one context (2026-11-13)

- Numbers: with context 256 and the harness default of 128 new tokens a prompt may have 128 tokens. Generation, default shape, random weights, stand-in tokenizer with 102 tokens, load average 24-27: CPU 238 tokens/s greedy (128 tokens in 0.54 s), 896-1067 tokens/s summed over 10 samples; MPS 34 and 139-157 tokens/s while another run was training on it.

- Not verified: with the real `lsllm.tok.Tok`. No tokenizer directory accepted by that class existed (`data/tok/q512` and `m512` are refused by it), so the completer is tested with a stand-in tokenizer only.

### D-tokenizer-1: Marker text is built with `tokenize` and checked by decoding it (2026-11-13)
- Decision: `lsllm.structure.to_markers` reads canonical text with the standard `tokenize` module (NEWLINE, INDENT and DEDENT tokens give the marker in front of every logical line; a token that spans several lines is a docstring and gets `<LF>`), then decodes its own result and raises `ValueError` unless the input comes back. `from_markers` is one call of the streaming class `MarkerDecoder` (`feed(piece)` returns the new text). ### D-tokenizer-2: One extra token `<BLANK>` makes the indentation level the whole decoder state (2026-11-13)
- Decision: marker text stays as in INTERFACES (an empty docstring line is `<LF><LF>`). The tokenizer writes an `<LF>` that is followed by another `<LF>` as the token `<BLANK>` (SentencePiece control symbol, id 3, `Tok.blank_id`; `Tok.pieces` shows it as `<LF>`). A token then turns into text knowing only the level: `<NL>`, `<IND>`, `<DEDk>`, `<LF>` = line break + indentation of the (new) level; `<BLANK>` = line break alone; any other token = its characters.
- Why: with two plain `<LF>` tokens a decoder must see the next token before it knows whether a docstring line gets indentation. `Tok.decode(ids, level)` and `level_after` carry only the level, so a sequence cut right after an `<LF>` could not be decoded in parts, and every user that works token by token (the model completer tracks the level per token, the UART script prints per token) would need a hidden flag. With `<BLANK>` any cut is exact; printing live is `text += tok.decode([t], level); level = tok.level_after([t], level)`.
- Numbers: runs of `<LF>` in the bootstrap set: 9,801 single, 4,048 double, 3 triple, so 4,054 `<BLANK>` tokens, about 0.2% of all tokens. Sequence length is unchanged; the cost is 1 of the 256 or 512 ids. Test: 483 functions cut at every token position, 81,855 cuts with vocabulary 256 and 67,976 with 512, all exact.
- Rejected: a flag next to the level (not in the `Tok` interface); a negative level after `<LF>` (a trap for every user of the level); one token for the pair `<LF><LF>` (wrong for two empty lines in a row); indentation after every `<LF>` (leaves spaces on empty docstring lines, so the round trip is no longer exact).

### D-bench-9: Corrections to D-bench-3, 4, 5 and 8 after more tests of the sandbox (2026-11-13 19:10)
- Decision (replaces the parts of D-bench-3 and D-bench-5 about writing): a sandboxed program cannot write any file. The private directory holds only the program (`main.py`) and is readable, not writable; `TMPDIR` is no longer passed (the environment is empty). Stdout and stderr are two nameless temporary files of the parent, each limited by the kernel to 2 MB (`FILE_MB`); the first 64 KB are returned. The watchdog no longer measures disk use and there is no 8 MB total. This is stricter than INTERFACES section 5 ("no file writes outside a private temp directory").
- Why: the 8 MB total of D-bench-5 was enforced by the parent only. `tools/guard.sh` kills the parent with `pkill -9` exactly when disk or memory is low (it killed one of my test runs at 18:53), and a child that keeps creating files would then have been limited only by its CPU seconds. Now the most a run can put on disk is 2 x 2 MB, enforced by the kernel with or without a parent. No reference solution needs to write: the reference results are unchanged (HumanEval 164/164, MBPP test 497/500, MBPP practice 461/464, custom test 200/200, 30 s timeout).
- Correction to D-bench-4, "Rejected": an address-space limit relative to the process's own size is not a memory limit on this macOS. With `RLIMIT_AS` or `RLIMIT_DATA` set to "current size + 192 MB" a program took 600 MB in 1 MB pieces without any error (the test stopped itself there); an uncapped variant under `ulimit -v` reported about 8,300 MB before MemoryError. Only a single block larger than the allowance is refused. So the footprint watchdog is the memory limit, and it works only while the parent lives.
- Open point (not solved): if the parent is killed with SIGKILL while a child is growing its memory in small pieces, nothing limits that child's memory until the kernel CPU limit ends it (timeout + 2 CPU seconds). The watchdog normally kills such a child within about 0.06-0.12 s, so the parent has to die inside that window. `tools/guard.sh` does not match sandboxed children (they run the base interpreter as `.../python3.12 -I -S main.py`); adding that pattern to its `pkill` would close the case in which the guard itself kills the parent.

### D-filter-1: The syntax filter is defined by tables: two bytes per token, 7 bytes of state, 17 abstract states (2026-11-13 21:50)
- Decision: `lsllm/filter_table.py` (`TableFilter`, same calls as `lsllm/filter.py`: `start`, `allowed`, `step`) is the binding definition of the filter; `docs/FILTER.md` explains it. Per token id: a class byte (25 classes) and a word-column byte. State: lexer state (17 values), first-word state (49), colon bit, indentation level, bracket depth (at most 8) with 2 bits per level. Before each choice the state is reduced to one of 17 abstract states and a token is allowed if `ALLOW[abstract state][class]` is 1. The step uses the class and two tables (`LEX` 17 x 25, `WORD` 62 columns x 49 states). All tables are built by running the characters of every token through two small automata; at run time no character is read.
- Why: the CPU cannot scan characters, and the integer reference must use the filter that the CPU uses. The per-token test in the argmax loop is `LD` class, `LUT`, `BZ` (3 instructions, 12 cycles).
- Numbers (tokenizer `data/tok/f512a`, 6,000 functions of `data/final/f512a/human_val.jsonl` and `human_train.jsonl`, 932,094 positions): accepted from start to end 5,997 (99.95%; the 3 others use `match`), `lsllm/filter.py` 5,984 (99.73%). Tables: token 1,024 + ALLOW 544 + LEX 544 + WORD 3,968 = 6,080 bytes. Cost estimate (not simulated): 512 x 12 = 6,144 cycles in the argmax loop plus about 180 instructions (720 cycles) once per generated token, together about 6,900 cycles, 0.7 to 1.2% of a token.
- Rejected: one mask byte per (state, token) as in SPEC Part D (the number of states is not bounded); bracket depth 12 (one function of 6,000 reaches depth 8, none goes beyond; 8 levels fit 2 bytes); adding `match` to the block keywords (it is also an ordinary name: `match = re.match(...)` would then be refused).

### D-filter-2: Block keywords are spelled through a table, not marked by flag bits on tokens (2026-11-13 21:50)
- Decision: the first word of every line is followed through a 49-state automaton (the 12 block keywords, their 34 beginnings, "keyword and over", "no keyword", "line start"). Each token has a column of the `WORD` table that says where it leads from every state; tokens with the same effect share a column (62 columns for f512a, 51 for boot256, 68 for boot512). The table is stored by column (64 bytes each), so any vocabulary fits.
- Why: the planned flag bits ("the token is a complete keyword", "the token is exactly a keyword") assume that a keyword is one token. In f512a only `def `, `if `, `for `, `with ` and `else` are; `while ` is `wh` `il` `e `, `elif ` is `e` `li` `f `, `try` is `tr` `y`, `class ` is `clas` `s `, `except` is `excep` `t`, `finally` is `f` `in` `all` `y`, `async` is `as` `y` `n` `c`. With flag bits alone the rule "a keyword line must end with a colon" would not hold for these.
- Numbers: with the table, the keyword rule agrees with `lsllm/filter.py` at every one of the 932,094 positions (no unexplained difference). Cost: one more byte per token and 3,968 bytes of table.
- Rejected: a "may be a keyword" state that lets such a line end with or without a colon (the partial version of this module: simple, but it switches the rule off for while, elif, try, except, class, finally, async); making these keywords single tokens in the tokenizer (a forced token `for` or `class` would also cut `format` and `classes`).

### D-filter-3: Four rules that lsllm/filter.py does not have (2026-11-13 21:50)

Canonical code contains none of them (the 6,000 functions pass). The random-text test only passes its independent check with the leading-space rule.
- Numbers: allowed sets equal to those of `lsllm/filter.py` at 375,061 of 932,094 positions (40.24%, the positions inside strings); equal at 931,803 (99.969%) when the four added rules are set aside (`#` and `\`: 556,748 positions, leading space: 34,821, end after colon: 11,559). The other 291: 285 inside `'''` strings (table filter more permissive, and right), 6 at bracket depth 8 (more restrictive). ### D-intref-1: One integer reference for a single token and for a batch, checked against a loop version (2026-11-13 21:55)
- Decision: `lsllm/intref/model.py` has one code path: `step(tokens)` advances every sequence of a batch by one token with numpy integers and keeps the KV cache as `K[l][row, g, p, j]` and `V[l][row, g, j, p]` (the layout of SPEC C.5); an int token is a batch of one. Every requantisation goes through one function that asserts the signed 24-bit range, records the largest |accumulator| per stream and, in trace mode, stores the accumulator (`name.acc`) and the int8 result (`name`). `IntCompleter` reads the prompt once, copies the cache per sample and drops finished samples from the batch. The test suite contains a second implementation written from the SPEC text with plain Python integers, one number at a time; both must give the same logits at every position.
- Why: a separate batched path would be a second model that can drift from the one the FPGA test vectors come from. The loop version is the independent reading of the specification.
- Numbers: 227 lines; identical logits to the loop version for 3 shapes (dyt/swiglu, rms/relu, dyt/relu with attn_norm recip) over a full context; 85 tests of the area in about 11 s, 270 MB. Real shape (260K parameters, T = 256): 297 validation windows of 256 tokens in about 20 s inside the QAT forward pass; the numpy reference is used for generation and for the bit-exact check.
- Rejected: int8 arrays with explicit widening (int32 everywhere is simpler and the range checks are explicit); a per-sequence Python loop for benchmarks (thousands of samples).

### D-intref-2: Sampling as on the CPU, vectorised with the LFSR cycle (2026-11-13 21:55)
- Decision: Gumbel-max sampling of SPEC Part D draws one `RND` per vocabulary entry in index order. `g0 = round(tau * 2^(f_l - 1) * ln(ln 512))`, which makes the smallest table entry 0 (the SPEC names g0 but does not define it). A batch row r starts its LFSR at `0xACE1 xor (seed + r)` (0 is replaced by 0xACE1). The 65,535 LFSR states are precomputed once in visiting order, so the V draws of a token are one indexing operation.
- Why: the sequence of random bytes must be the one the CPU produces, otherwise sampled outputs cannot be compared with the board.
- Numbers: test: the vectorised draws equal `rnd()` called V times per token for 3 rows and 3 tokens; 4,000 draws from fixed logits are within 0.06 of softmax(logits) at temperature 1.
- Rejected: numpy's random generator (not the CPU's bits); a Python loop per draw (512 draws per token per sample).

### D-qat-1: QAT forward = the exact integers in float32, with three gradient rules (2026-11-13 21:55)
- Decision: `QatModel.forward` computes SPEC Part C for a whole (batch, time) tensor; every value is a whole number below 2^24 in a float32 tensor. Trained parameters are latent float weights in real units, rounded and clamped to -127..127 in the forward pass, and the per-head score offsets in nats (they become the preloads `c_s`). Gradients: (1) rounding of weights, floor shifts and clamps pass the gradient of the unrounded value (the shift contributes the factor 2^-sh); (2) a table passes the derivative of the smooth function it samples (tanh, 1/sqrt, SiLU, exp, 1/m), stored as a second 256-entry table; (3) a ReLU inside RQ stops the gradient where the accumulator is negative, except at the logits, where the floor at 0 is treated as a clamp so that a token below the floor can still be pulled up. After each optimiser step the latent weights are clipped to what int8 holds at their scale. The loss is the cross-entropy of `u * 2^-f_l`.
- Why: the model that is trained is the model that is exported; there is no separate "fake quantisation" graph whose difference to the CPU would have to be measured.
- Numbers: QAT forward and integer reference give identical logits at every position for 5 shapes (calibrated) and 15 scrambled models (random int8 weights, random shifts, shift 0 included), and after 20 optimiser steps. Real shape on the CPU with 2 threads while the GPU trained: 2,441 tokens/s at batch 8 x 256, peak memory footprint 607 MB (batch 32 would need about 1.5 GB: the attention tensors are batch x heads x T x T).
- Rejected: fake quantisation of a float graph (not bit-exact); a Python loop over positions (the brief forbids it); gradient through the clamp set to zero (saturated values could never come back).

### D-qat-2: Calibration: scales from the float checkpoint (2026-11-13 21:55)
- Decision: `calibrate(float_model, token_batches, pct=99.9, attn_norm="none")`. Weight matrices: the largest f at which the largest weight fits in 127 (no clipping). Activations: the largest f at which the 99.9th percentile of |value| on the calibration batches fits. Residual matrices have no free scale (f_W + f_h = f_x + 8): f_h is set halfway between "the weights fit" and "h fits". Folded into the float weights first: per-channel norm gains into the matrices that read the norm, the embedding scale into E, 1/sqrt(d) and the 127/128 of the two RoPE tables into Wq, the 127/128 of the EXP table into Wo. Logits: f_l is the largest scale at which the observed range of the top logit plus a tail of ln(V) + 3 nats fits in 0..127; of the offsets that achieve this the one nearest to 0 is used.
- Why: the maximum for weights because a clipped large weight changes the function at once, while QAT can still shrink it later; a percentile for activations because a few outliers would cost every other value one bit. The offset nearest to 0 because the logit preload `c_l` is a 16-bit value: `c_l = offset * 2^(f_l + sh_l)`, so a large offset forces a small shift `sh_l` and leaves few bits for the final norm output.
- Numbers (data/tok/f512a, 297 validation windows of 256 tokens, 16 calibration windows from the training stream, no QAT step): cap checkpoint runs/a/a2_cap at step 300: float 3.8955, integer 3.9062 nats/token (+0.011); 50 prompts: same greedy token at 86.9% of 1,600 new positions. Toy DyT model before the offset rule: final norm amplitude 4.57 (11 levels, top logit clipped at 58% of the positions); after: 9.1 and no clipping.
- Rejected: per-row scales (SPEC B.5); maximum for activations; clipping the weights by percentile (left to QAT).
- Limits found: (1) a per-channel gain of the final norm cannot be folded into the tied matrix E; its mean goes into the final table and the rest is left to QAT. (2) With `c_l` limited to 16 bits, `sh_l` is at most 8 to 10 for usual offsets; this is enough for the rms checkpoints (final norm output about +-30) and thin for small-logit models.

### D-qat-3: A softmax checkpoint loses about 1 nat when mapped to unnormalised cap attention; recip is implemented (2026-11-13 21:55)

### D-arch-2: Attention must be normalised; unnormalised table attention rejected (2026-11-13 22:10)
- Decision: the attention output is divided by a power of two derived from the sum of the table weights (`attn_norm = pow2`, SPEC C.6), with exact division by a reciprocal table (`recip`) as the fallback. The CPU gets two small instructions for it: `NRM Rd` (number of significant bits of ACC) and `RQV Rd, Rs` (requantise with the shift taken from a register).
- Why / numbers: the float stand-in of unnormalised attention (7-bit exp table referenced to the top code, values mixed with the raw weights) stopped learning: validation loss 3.91, 3.90, 3.98, 4.03 nats/token at steps 300 to 1,200 with the training loss rising, against 3.55, 3.08, 2.92, 2.89 for softmax on the same data and schedule (runs `a/a2_cap`, `a/a1_base`); its samples did not parse at all (syntax_ok 0% on the custom practice set). Cause: 7-bit weights cannot express "a small share for each of many tokens" (the smallest non-zero weight is 1/127, so 256 keys weigh at least 2.0 in total), and nothing bounds the sum as the context grows.
- Rejected: a constant shift per layer (same problem); a shift chosen from the position (does not see how many keys are active).

### D-ls-cpu-5: L1 is a second instruction table and a second simulator class; cycles are counted per address (2026-11-13)
- Decision: `isa.TABLE_L1` holds the L1 instruction set of SPEC Part A (the L0 rows that do not change are reused, the rows of MVP, LD, ST, MAC, SETP0/1 are replaced, LUT, TX, RND, MVL, MVH, LD/ST through P2, MACL and the six CPP are added); `encode` and `decode` take the table as an argument. `iss.L1` is the L1 machine: one data memory (an `array('b')` with a numpy view of the same bytes), P0..P2 of 20 bits, LEN, `lut_base`, the UART bytes in `tx`, the LFSR. `L1` does not add cycles while running: it counts how often every program address was executed (`count`) and the multiply-adds of its streams (`elems`); cycles = 4 * sum(count) + sum(elems). Streams of 24 or more elements are one numpy dot product; the exact overflow flag is only computed when |ACC| + 16,384 n can reach 2^23. Level L0 (`LS`, `TABLE`, the assembler) is untouched.
- Why: the cost model needs the same execution counts priced in several ways (L1, classic MAC, every L2 what-if) and per component; per-address counts give all of them from one run. One table per level keeps "L0 unchanged" true by construction (the 167 L0 tests still pass).
- Numbers: 12 tests in `tests/test_ls_l1_iss.py` (every encoding of the SPEC table, every new effect, n + 4 cycles, sticky overflow inside a stream, all 65,536 words decode to at most one instruction and back). One token of the stories260K shape at context 256 is 110,936 instructions and 868,272 cycles and runs in 0.06 to 0.2 s (the brief asked for one or two seconds).
- Rejected: one class with a level switch (every effect would test the level); summing cycles per region while running (the what-if prices could then not be recomputed without another run).
- Not modelled: the UART FIFO never fills (TX always costs 4 cycles; at 115,200 baud two bytes per token allow 5,760 tokens/s), IN/OUT timing, clock enable. The L1 text assembler was not written: the generator emits (mnemonic, operands) directly and `gen.listing` prints the program in the notation of the design document.

### D-ls-cpu-6: The CPU never computes an address from the position or from the token id: position records and a token table (2026-11-13)
- Decision: two tables built by the generator replace all address arithmetic. (1) One record per position p (9 + 2 d bytes): the address of the next record, p + 1 as count and as LEN, p, the address parts of the key slot of p, and the RoPE values of p in the order the program reads them ([C, -S] pairs, then [S, C] pairs). At the start of a token the program follows the link kept in `scratch.rec`, copies the record there (12 cycles per byte) and loads LEN. "Advancing the position" is that copy; a link with page 0 means the context is full and the program halts. (2) Three bytes per token id (low byte, bits 11..8, bits 19..12 of the address of its row of E), read with `MVP P0, hi, lo`.
- Why: L1 has no carry flag, no multiply into a register and no way to read a pointer back, so p * d, p * 2 d and token * D cannot be computed cheaply; only MVP/MVH can build a pointer from registers. With the records every value that depends on p is a byte that is read. The scheme works for any head size (no power-of-two restriction) and costs no instruction per layer.
- Numbers (stories260K, H = 8): records 6,400 bytes (the RoPE tables alone would be 4,096), token table 1,536 bytes; per token 420 cycles of bookkeeping (record copy 300) and 856 cycles for the embedding (768 of them the copy of the row); H = 2 (d = 32): records 18,688 bytes, bookkeeping 996 cycles.
- Rejected: 16-bit counters in scratch updated every token (carry detection without a carry flag only works when the step divides 256); requiring D to be a power of two and shifting the token id (about 40 instructions, and D = 80 or 96 would not work); reading RoPE directly from the table with a pointer set from the record at every head (about 32 cycles and 6 words per head instead of 4 cycles and 1 word).
- Consequence for the host: the "position variable" is the 3-byte link in `scratch.rec` (`gen.set_position`), the token id is 2 bytes in `scratch.token` (high byte first). T <= 256 and V <= 4,096.

### D-ls-cpu-7: Value rows live in 256-byte slots addressed with the loop counter; keys follow in the same block (2026-11-13)
- Decision: the row V[l][g][j][0..T-1] of SPEC C.5 gets a 256-byte slot, so the position is the low byte of the address. Rows are visited in loops of at most 16 passes; the row of the pass with R3 = r is slot r mod 16 of the page of its chunk. The cache write is `LD R0,[P0]+ ; MVP P2,R3,R2 ; ST R0,[P2] ; DJNZ` (R2 = p, 16 cycles per value) and the value-mixing row starts with `MVP P1,R3,Rz` where Rz is the zero byte of the rounding preload already held in R1:R2. With d < 16 the slots 1..d are used and the key block K[l][g] (T * d bytes) is placed right behind them, ending in the unused slot 0 of the next block; with d >= 16 the keys get their own pages. The rotated key is written straight into the cache by the RoPE loop (P2 is set from the record), so keys are never copied.
- Why: the value-mixing stream must read V[j][0..p] contiguously, so the write is a scatter; in both loops all four registers are taken (R0 result, R1:R2 preload, R3 counter), and R3 is the only register that changes per row. Using it as the slot number costs no register and no instruction.
- A trap found and handled: with T = 256 a row in slot 15 ends exactly at the end of its page, the stream leaves P1 in the next page, and the next `MVP` (low 12 bits only) would land one page too high. In chunks that use slot 15 (d >= 15 and T = 256) the page is therefore set again in every pass (`LDI R0,page ; MVH P1,R0`, 8 cycles per row): the row costs p + 37 instead of p + 29 cycles. The same rule is why every vector that a pointer rewinds is placed so that it ends before the end of its page (`alloc`, checked by `Emitter.rewound`).
- Numbers: KV cache of stories260K (H = 8, G = 4): 81,920 bytes, exactly 2 L G d T, in 20 blocks of 4,096 bytes; cache writes 3,500 cycles per token; value mixing 92,000 cycles at context 256.
- Rejected: storing V position-major like K (the mixing stream would need a stride); unrolled `SETP1` per row (6 words per row, 1,920 words for the five layers); always streaming whole rows of T against a zero-padded e (cost T + 24 per row at every position: 82,000 cycles per token at context 16 instead of 15,200).

### D-ls-cpu-8: The instruction sequences of the loops, and what was not done (2026-11-13)
- Decision (cycles at L1, all measured in the simulator by `tests/test_ls_gen_prims.py`): linear row `SETP0 x ; LDA R1,R2 ; MAC #n ; RQ ; ST R0,[P2]+ ; DJNZ` = n + 24 (n + 28 with a LUT after RQ; n = 1 uses the classic MAC: 28; n = 256..510 uses two streams: n + 28); residual row `LD R1,[P2] ; LDA R1,R2 ; SETP0 h ; MAC #n ; RQ R0,8 ; ST R0,[P2]+ ; DJNZ` = n + 28; score `SETP0 q ; LDA ; MAC #d ; RQ ; LUT EXP ; ST ; DJNZ` = d + 28 per key; value mixing = p + 29 per row (p + 37, see D-ls-cpu-7); RoPE `LDA ; MAC #2 ; RQ R0,7 ; ST ; DJNZ` = 22 per rotated value, two passes per head; element-wise product `LDA ; MAC ; RQ ; ST ; DJNZ` = 20; table map `LD ; LUT ; ST ; DJNZ` = 16; rms scaling `SETP1 r ; LDA ; MAC ; RQ ; ST ; DJNZ` = 24 per element (r is kept in a memory cell so that the product is a one-element stream); argmax `LD ; SUB ; LUT RELU ; BZ ; DJNZ` = 20 per logit plus 16 per new maximum. The SiLU table is applied inside the W1 row loop (4 cycles per row instead of a 16-cycle pass). Weights are stored in reading order, so P1 is set once per group of matrices and never per row. Layers and heads are unrolled.
- The argmax uses a table max(v, 0) instead of the sign table of SPEC A.2: the LUT result is the difference itself, so a new maximum is taken with one `ADD` (the candidate does not have to be read again). It runs in blocks of 256 logits; the index is rebuilt from the value of R3 at the maximum and a block number stored on each update.
- Why two passes for the output layer (store all logits, then argmax): in the row loop all four registers are in use (preload c_l in R1:R2), so a running maximum would need two LDI per row, as much as the LD and DJNZ it saves; and the stored logits are what the tests compare and what sampling and the syntax filter will need.
- Numbers: stories260K, dyt, swiglu, context 256: 868,272 cycles = 115.2 tokens/s at 100 MHz; 424,988 multiply-adds = 48.9 % of the cycles; scores 370,080, feed-forward 215,660 + gating 20,780, value mixing 92,000, q/k/v 56,512, output layer 45,080, attention output 29,580, RoPE 12,180, norms 11,348, argmax 10,276, cache writes 3,500, embedding 856, bookkeeping and UART 420. Program 3,135 words (3,343 with rms).
- Rejected or not done: (1) remembering constants in registers to skip repeated LDI (measured: 116 words and 464 cycles saved, 0.05 %; without it the cycle count depends only on shape, options and position, never on the constants of a model); (2) unrolling the score loop twice (2 cycles per key, about 2.4 % at context 256, for about 360 more words and a jump into the middle of the loop for odd counts); (3) folding the gating product into the W3 row loop (needs two more constants than there are registers: 32 extra cycles per row against 20 for the separate pass); (4) writing v straight into the cache from the Wv row loop (no register for p).
- Limits: the ROM of 4,096 words holds H <= 8 (H = 8, G = 8, rms: 3,983 words). H = 16 needs 5,183 (G = 4) to 5,823 (G = 8) words, i.e. a 13-bit PC, or loops over heads, which need call/return or pointers set from registers per head. At most 6 layers (16 tables: 2 L + 1 norm tables, EXP, RELU, SILU). D, F <= 510; rounded shifts <= 15 (the preload 2^(sh-1) must fit 16 bits).

### D-ls-cpu-9: The cost model is the simulator run on zero weights; classic and L2 numbers are other prices of the same counts (2026-11-13)
- Decision: `cost.cycles_per_token(cfg, options, pos, **switches)` generates the program of the shape with zero weights, runs one token at position `pos` in `iss.L1`, and prices the per-address counts with `cost.price`. - Checked: for 5 shape/position pairs x 4 option sets the cycles of a model with random weights and a random cache equal the cost on zero weights component by component, except the argmax, which differs by exactly 16 cycles per new maximum (24 in a last block of fewer than 256 logits); at most 127 maxima, so at most 2,032 cycles (0.2 %) above the table. ### D-ls-cpu-10: attn_norm = recip (SPEC C.10) is not generated (2026-11-13)
- Decision: `gen.build` raises NotImplementedError for `attn_norm = recip`.
- Why: C.10 computes `a = rq(A[j], x + 7)` with an exponent x that depends on the data (15 values). The shift of RQ is a constant of the instruction, there is no indirect jump and no call/return, and heads are unrolled: at L1 this needs one copy of each value-mixing loop per exponent, about 300 words per head, about 12,000 words for H = 8 and five layers. It fits the ROM only with a hardware change (PROPOSAL: an RQ whose shift comes from a register) or with shared routines and a return dispatch written as compare-and-branch chains.
- Numbers: none measured. With a register-shift RQ the extra cost would be one stream over e per head (p + 1 + about 16 cycles), a search of at most 15 compare steps per head, and one multiply and RQ more per value row (about 16 cycles).

### D-arch-3: Final integer attention: exact row maximum, 7-bit table, reciprocal division (2026-11-13 22:45)
- Decision: SPEC C.6 (v0.4). Score codes are unsigned 7-bit at about 4 codes per nat with a calibrated offset per head; the CPU finds the row maximum, looks up `round(127 * exp(-d / kappa))`, and divides the mixed values by the sum with a reciprocal table (two small instructions, `NRM` and `RQV`). The float model is trained with ordinary softmax.
- Why / numbers (trained softmax model `c/e0_softmax_more`, 40 validation windows of 256 tokens, same weights, no retraining):
  - float softmax 2.8684 nats/token;
  - this design: 2.8703 at kappa 4 and target code 84 (+0.0019); between +0.0003 and +0.0116 for kappa 3 to 5 and targets 72 to 96; high clipping must stay near zero (kappa 8, target 112: +0.25);
  - exact maximum, exact division, signed codes (`maxnorm`): 2.8681 (+0.0);
  - exact maximum, power-of-two division instead of the reciprocal table (`maxpow2`): 3.1119 (+0.24);
  - table referenced to a fixed top code with a per-head offset instead of the row maximum: 3.42 (exact division) and 3.70 (power of two) right after conversion, and 3.58 after 300 fine-tuning steps (run `c/e1_capnorm_ft`), against 2.85 for softmax trained for the same extra steps (`c/e0_softmax_more`). Training that form from scratch reached only 4.49 at step 300 (`a/a3_capnorm`, softmax 3.55). The row maximum of a head varies by 1.2 to 12 nats between positions (10% to 90% range), far more than the 5.5-nat window of a 7-bit table.
- Cost on the CPU: the maximum and the second pass over the scores are the price (first estimate: about 20 to 40 cycles more per score than a table inside the score loop; measured by the cost model). This makes the number of heads the main speed lever.
- Rejected: fixed-reference tables (cheap, but they lose 0.7 nats); a power-of-two normaliser (0.24 nats).

### D-qat-5: Calibration and QAT for SPEC v0.4 attention (2026-11-13 22:56)
- Decision: `calibrate(float_model, token_batches, pct=99.9)` accepts softmax checkpoints only. Scores: 4 codes per nat (`frac["s"] = f_q + f_k - sh_s = 2`); the offset of a head puts the median over positions of its largest score at code 80 (the rule of `tools/attn_proxy_eval.py`); if q and k are too coarse for 4 codes per nat the shift is 0 and the table of that layer is built for the codes per nat that remain (reported in `notes`). Peak 478 MB at batch 2.

- Not verified: a QAT run of useful length (not allowed here); memory above batch 4 (extrapolated: 1.1 GB at 16, 1.8 GB at 32); the DyT stream-range rule on a trained DyT checkpoint (none exists; DyT is dropped by D-arch-1); which part of the +0.038 belongs to which tensor.

### D-ls-cpu-12: The attention of SPEC v0.4 on the CPU: instruction sequences (2026-11-13)
- Decision (cycles at L1, measured in the simulator by `tests/test_ls_gen_prims.py`; replaces the score and value-mixing lines of D-ls-cpu-8 and all of D-ls-cpu-10). Per key: `SETP0 q-1 ; LD R0,[P0]+ ; LDA R1,R0 ; MAC #d ; RQ R0,sh,relu ; ST R0,[P2]+ ; SUB R0,R2 ; LUT R0,RELU ; ADD R2,R0 ; DJNZ` = d + 40 (code and running maximum in one loop, no branch: max <- max + relu(code - max)), then a second pass `LD R0,[P0] ; SUB R0,R2 ; LUT R0,EXP_l ; ST R0,[P0]+ ; DJNZ` = 20 (weights in place through P0). Per head: one stream of the weights against a row of ones (p + 5), `NRM` (k), `LDI 7 ; SUB ; RQV` (mantissa), `LUT RECIP` (r). Per value row: `MVP P1,R3,R1 ; SETP0 e ; LDA R1,R1 ; MACL ; LD R0,[P0]+ ; RQV R2,R0 ; LD R0,[P0]+ ; MUL R2,R0 ; LDI R0,half ; LDA R1,R0 ; ADDP ; RQ R0,sh_o ; ST R0,[P2]+ ; DJNZ` = p + 57 (p + 65 when the page of P1 has to be set again).
- Why: both loops need five values in four registers. Score loop: R3 counter, R1 high byte of c_s, R2 maximum, R0 code; the low byte of c_s is a memory byte placed just before the rotated query, so the rewind of P0 reads it for 4 cycles instead of holding a register. Value rows: R3 counter, R1 = 0, R0 and R2 temporary; k, r and the page of the rows are three bytes right after the weights, exactly where P0 stands after every stream over e, so they are read without setting a pointer. The reciprocal product uses the baseline MUL and ADDP (no memory operand needed).
- Numbers (stories260K shape, H = 8, G = 4, dyt, swiglu, context 16 / 64 / 256): 489,532 / 637,372 / 1,228,732 cycles = 204.3 / 156.9 / 81.4 tokens/s; scores, maximum and exp are 45,920 / 176,480 / 698,720 of them (d + 60 per key against d + 28 for the fixed-reference table of SPEC v0.2). H = 4, G = 2: 463,484 / 552,764 / 909,884 (215.8 / 180.9 / 109.9 tokens/s). H = 2, G = 2: 484,428 / 544,428 / 784,428 (206.4 / 183.7 / 127.5 tokens/s).
- Rejected: maximum in a separate pass (d + 24 and 20: 4 cycles per key more); a separate loop for the reciprocal product (p + 29 and 24 per value: same cycles for d = 8, 7 words more per layer); the two-register preload in the score loop with the maximum kept in memory (more than 12 cycles per key).
- Not done (possible savings): c_s restricted to 257 * a (then `LDA R1,R1` and no read: 4 cycles per key less, 40,960 cycles at context 256 for H = 8; needs a SPEC change); two weights per pass of the second loop (2 cycles per key less, needs a second count byte in the position record).

### D-ls-cpu-13: One piece of program per layer for all query heads, driven by head records (2026-11-13)
- Decision: the code of a query head (RoPE of q, scores, weights, division, value rows) is written once per layer. `Emitter.for_records` runs it for a chain of 13-byte records (link to the next record, address of the head in q, address of its keys, c_s, first page of its value rows, address of its output); each record is copied to a fixed place first, and the rotated query is written to a fixed buffer, so every `SETP0` in the loops is a constant. Key/value heads stay unrolled.
- Why: with SPEC v0.4 an unrolled head needs about 76 words (estimate from the sequences above); 40 heads plus the rest would be about 4,200 (dyt) to 4,400 (rms) words for the stories260K shape with H = 8, above the 4,096-word ROM. There is no call and return, so sharing code means reading the addresses from memory.
- Numbers: program 1,855 words (dyt, swiglu) and 2,061 (rms, swiglu) for H = 8, G = 4; 2,701 for H = 8 or 16 with G = 8. Cost: 212 cycles per head (13 bytes copied at 12 cycles, 14 instructions), 8,480 cycles per token for 40 heads = 1.7% at context 16 and 0.7% at context 256. Data: 520 bytes of records.
- Rejected: unrolled heads (do not fit); also sharing the key/value-head code (20 heads, about 500 words: not needed).

### D-ls-cpu-15: The complete program: prompt buffer in memory, prefill skip, the ending token is sent (2026-11-13)
- Decision: `gen.build(..., prompt=True)` makes the program that runs alone: a prompt buffer in data memory (`prompt.ids`: byte p = high byte, byte 256 + p = low byte of prompt token p; `prompt.left` = tokens still to feed, 1..min(T, 255); written by `gen.set_prompt` into the image or the memory file), fed one position at a time. A prompt token that is not the last jumps back to the start after the layers: no final norm, output layer, argmax, UART. With the tokenizer tables (`tf=`) the stop rule of `IntCompleter` runs on the CPU (end of text, or `<NL>`/`<DEDk>` back to level 0); the token that ends the text is sent before HALT. Without options the program is word for word the old one.
- Why: the CPU has no UART receiver, so the prompt must be in memory. The ending token is sent because a HALT is silent: the host needs a mark for "the text is over" (the host drops it, as `IntCompleter` does). A second level byte follows `Tok.level_after` (every line break counts), separate from the level of the filter (line breaks inside strings do not count there).
- Numbers: stories260K shape, rms, swiglu, H = 8, G = 4: prefill token 439,740 / 587,580 / 1,178,940 cycles at context 16 / 64 / 256 against 496,768 / 644,608 / 1,235,968 for a generated token: 57,028 cycles saved per prompt token (11.5% / 8.8% / 4.6%). Prompt test and stop rule cost 164 cycles per token. Program 1,736 -> 1,798 words (H = 2, G = 1).
- Rejected: a prompt count of two bytes (a prompt of 256 tokens leaves no room to generate more than one token); stopping without sending the ending token; a budget of new tokens in the program (the host can count).

### D-ls-cpu-16: The syntax filter on the CPU: class byte and LUT of the copied ALLOW row, state step with [row][byte] tables (2026-11-13)
- Decision: as FILTER.md section 8: before the argmax the abstract state is computed, its 32 bytes of ALLOW are copied into one `LUT` table, and the argmax loop reads the class of every token id (`LD [P1]+`, `LUT`, `BZ`). The comparison table of the filtered argmax is v + 1 for v >= 0 (the stored maximum is value + 1 and starts at 0), so the first allowed token wins at any value. A row of ALLOW in which no token of the vocabulary is allowed is written as all ones when the image is built (= unfiltered, as `IntModel.choose`). The step uses tables read with `MVP P, Rrow, Rbyte ; LD` (16 rows of 256 bytes in one page): new level [change][level] saturating at 255, word table as byte 64 k + w with the two address bytes of 64 k stored per token id, the string automaton as one LUT of deduplicated columns (6 + 1 for control tokens). Line breaks and control tokens get their own word column (reset, identity) so that the step needs one branch on "in code" and three on brackets. The bracket stack is one byte per level holding abstract state + 1.
- Why: no call, no indirect jump, no signed compare, four registers: tables instead of tests. Only L1 instructions are used; no new instruction was needed.
- Numbers: + 6,748 cycles per generated token (12 per token id + 604; 1.4% at context 16, 0.5% at 256 for H = 8, G = 4), 200 cycles per prompt token, 135 program words, 9 more LUT tables (so at most L = 16 layers with filter and sampling), data memory + 8,192 to 16,384 bytes with alignment. FILTER.md estimated 6,900.
- Rejected: a mask byte per (state, token) (17 V bytes; the class byte needs V + 544); two bits per stack level (needs shifts); keeping the level in 0..127 with ADD and the RELU table (wrong after 128 `<IND>` in a row).

### D-ls-cpu-17: Sampling is one pass over the logits before the argmax (2026-11-13)
- Decision: with `temperature > 0` the program replaces u[j] by (u[j] >> 1) + GUMBEL[RND] for every token id in id order (`LD, SHR, RND, LUT, ADD, ST, DJNZ`), then runs the same argmax (plain or filtered). GUMBEL is `lsllm.intref.model.gumbel_table(temperature, f_l)` as one more LUT table; temperature 0 emits no RND and no table.
- Why: the argmax loop has no free register for the random byte (candidate, maximum, index, counter). One RND per token id, also for ids the filter forbids, is then automatic and equals `IntModel.choose`.
- Numbers: 28 cycles per token id: + 14,348 cycles per generated token at V = 512 (2.9% at context 16, 1.2% at 256 for H = 8, G = 4); 17 program words. Folding it into the argmax loop would save 12 cycles per token id (6,144) and needs the index of the maximum kept in memory.
- Rejected: sampling inside the output-layer loop (no free register either).

### D-arch-4: The LFSR is 32 bits (2026-11-13 23:15)
- Decision: `RND` uses a 32-bit LFSR, polynomial x^32 + x^22 + x^2 + x + 1 (bit = s[0] xor s[10] xor s[30] xor s[31], shifted in at the top), reset 0xACE1ACE1 with the 16 switches xored into the lower half; `RND Rd` advances 8 steps and returns bits 31..24. Changed in SPEC A.1/A.2, `lsllm/ls/isa.py`, `lsllm/ls/iss.py`, `lsllm/intref/model.py` and their tests.
- Why: the review of the integer reference found that with 16 bits one sampled token at V = 512 uses 512 x 8 = 4,096 steps of a period of 65,535, so after 16 tokens the noise of token id j is the earlier noise shifted by one bit. Sampled scores (pass@10) would rest on correlated noise.
- Numbers: period 2^32 - 1, checked in `tests/test_intref_model.py` by the order of the step matrix over GF(2) (the power 2^32 - 1 is the identity, the powers (2^32 - 1) / p for p = 3, 5, 17, 257, 65537 are not). Hardware: 32 flip-flops and about 8 LUTs for one byte per clock (research/09, table 6.2), against 16 flip-flops. Batch sampling in the reference uses four 256-entry tables (the LFSR is linear): 3.5 ms per token for 10 samples.
- Rejected: keeping 16 bits (correlated noise); 24 bits (period 16.7 million = 4,096 sampled tokens: enough for one answer, but 32 costs the same logic).

### D-data-5: Renaming augmentation (2026-11-13 23:00)

New names are drawn from the 419 parameter and variable names that at least 20 corpus functions use, weighted by count^0.75; a name is replaced with probability 0.75. ### D-ls-cpu-18: Attention window: the KV cache is a ring of W slots driven by the position records (2026-11-13)
- Decision: with `cfg.window = W` (0 < W <= T) the cache of a layer and key/value head holds W positions. The record of position p carries the count min(p + 1, W) (loop count of the score loop and stream length LEN), the key address of slot p mod W, and one more byte at its end, p mod W, which the cache write of the values uses instead of p. Nothing else changes: the score loop and the value rows read the first `count` slots, RoPE comes from the record of the absolute position, the prompt buffer is still read at byte p. `window = 0` gives the program, the image and the memory map of before, byte for byte (48 builds compared with the generator saved before the change).
- Why: the CPU never computes an address from the position, so a ring costs no instruction: only the table of records changes. The order of the keys inside the ring does not matter because scores, maximum and sums run over a set.
- Numbers: stories260K shape, rms, swiglu, H = 2, G = 1, cycles at context 16 / 64 / 256: W = 0: 456,840 / 516,840 / 756,840; W = 64: 454,292 / 514,292 / 514,292; W = 128: 454,292 / 514,292 / 594,292. One more record byte costs 12 cycles per token; with W < 256 a value row never ends at the end of its page, so the page of P1 is not set again per row: 2,560 cycles less for this shape (H = 8, G = 4 has no such rows: + 12, e.g. 644,456 at W = 64 from context 64 on). Data memory 374,016 -> 351,488 (W = 64) and 353,536 (W = 128) bytes: keys 40,960 -> 10,240 / 20,480; the value rows keep 256-byte slots, of which W bytes are used (unused bytes 5,566 -> 44,221 / 25,789).
- Rejected: value rows in slots of W bytes (the address of a value byte is `MVP P, row, slot`: row in bits 11..8, so a slot is 256 bytes; smaller slots need an addition per access); reordering the ring so that the oldest key comes first (not needed for a sum).

### D-shape-1: The Tier A budget is counted on the real memory image: 450,560 bytes for everything (2026-11-14 00:05)
- Decision: a Tier A shape is inside the budget only if the data memory image that `lsllm.ls.gen` lays out for the complete program (weights, E, KV cache, lookup tables, position records with the RoPE tables, filter tables, prompt buffer, scratch, alignment) is at most 110 block RAMs of 4,096 bytes = 450,560 bytes. `tools/fit_budget.py` finds the largest feed-forward width F per shape under this rule; `tools/pareto.py` marks runs over it.
- Why: the first shape search counted parameters + KV cache + 4 KB of tables. The generated image is larger: for 2 layers x 160 with F = 198 it is 517,888 bytes, not 449,056. The difference is the position records (43,264 bytes: the RoPE tables cost T x head size bytes, 160 per position here), the filter tables (10,272), alignment (10,681) and small regions. All of them are tables or state in block RAM, so they belong to the budget of the brief.
- Numbers: largest F inside 450,560 bytes (2 heads, 1 KV head, ReLU feed-forward, T = 256): 2 x 160: F = 92 (295,200 parameters); 2 x 144: 178 (301,392); 2 x 128: 304 (320,128); 3 x 128: 96 (287,616); 3 x 112: 182 (293,328); 3 x 96: 325 (319,968); 4 x 80: 286 (301,520); 5 x 64: 352 (320,192). With 4 query heads on 1 KV head the records and the cache halve: 2 x 160: F = 219 (350,880); 2 x 144: F = 301 (351,504).
- Consequence: every run of `runs/p` with "relu" and a budget-filling F (363,040 to 379,520 parameters) is over the budget and is kept only as evidence for the trend (wide and shallow learns faster). The search is repeated in `runs/q` with the F values above.
- Rejected: counting only weights, KV cache and the 256-byte tables (leaves 50 to 70 KB of tables uncounted); using the full 2^19 bytes (not the brief).

### D-train-2: The loss counts prompt tokens one tenth (2026-11-14 00:30)
- Decision: `lsllm.train.run --prompt-weight 0.1`: tokens that a benchmark prompt already contains (signature line and docstring) count 0.1 in the training loss, the body counts 1. The checkpoint of record is then chosen by the body loss on the validation text. The run reports both losses.

- Numbers (3 layers x 96, SwiGLU 224, 600 steps, same data and seed): weight 1.0: validation 3.0893 over all tokens, 3.0778 over body tokens; practice-solution loss 43.6 (custom) and 173.2 (MBPP) nats per solution. Weight 0.1: 3.3367 over all tokens, 3.0777 over body tokens; practice-solution loss 41.6 and 169.9. The body loss is unchanged, the loss on the practice solutions falls by 4.6% and 1.9%, and the all-token loss rises because the docstring is no longer learned.
- Consequence for reporting: "validation loss" of the final models is given over all tokens and over body tokens; comparisons with runs before this decision use the body loss.

### D-arch-5: The embedding lookup shifts E down to the scale of the stream (SPEC v0.6) (2026-11-14 01:30)
- Decision: `x = rqr(E[token], sh_e)`. The tied matrix E keeps the scale at which its largest weight fits int8 (this is what the output layer reads); the lookup shifts the row right by `sh_e` bits with rounding. `sh_e = 0` is the old plain copy. In SPEC C.1, the integer reference, QAT, calibration; the LS program gets it as a requantisation per element (a stream of one product against the row of ones).
- Why: without the shift E had to use the scale of the residual stream. On the final shape that left E the integers -16..16.
- Numbers (checkpoint of `runs/f/A1`, step 3,000, 64 validation windows, body tokens): float 1.9606. E rounded to steps of 2^-5 in the float model: +0.0315 nats; 2^-6: +0.0110; 2^-7: +0.0015. Integer model after calibration only: 2.0337 before the change (sh_e = 0, E in -16..16), 2.0237 with sh_e = 3 (E in -126..126, sh_l = 10, c_l = 24,567 still inside 16 bits). The gain in the integer model (0.010) is smaller than in the float experiment: other rounding dominates the remaining gap of 0.063, which quantization-aware training has to close.
- Cost on the CPU: the generator does the shift with one more lookup table (rqr of one byte is a function of that byte): 4 D cycles per token more than the copy, 640 cycles at D = 160 (0.12% of a token at context 64), measured on the generated program (D-ls-cpu-19).
- Rejected: a larger scale for the whole stream (later layers would saturate); an untied output matrix (twice the embedding memory).

### D-ls-cpu-19: The embedding shift of SPEC C.1 is a lookup table, not a product with 1 (2026-11-14)
- Decision: with `sh_e` > 0 the program reads the embedding row through one more LUT table EMB that holds rqr(v, sh_e) = clamp((v + 2^(sh_e - 1)) >> sh_e) for every byte v: `LD R0, [P1]+ ; LUT R0, #EMB ; ST R0, [P2]+ ; DJNZ`. With `sh_e` = 0 or absent the copy loop of before is generated and program, image and memory map are byte-identical (20 builds compared with the generator saved before the change). `cost.dummy_model` takes the shift as `options["sh_e"]`.
- Why: rqr of one int8 value is a function of one byte, and `LUT` is a primitive of SPEC B.2. The result is bit for bit that of the stream SPEC C.1 describes, at 16 instead of 20 cycles per element (`LDA ; MAC ; RQ ; ST ; DJNZ`), and without a row of D ones (the ones row has T bytes, and D can be larger than T).
- Numbers: + 4 D cycles per token at any shift 1..15: + 256 at D = 64 (stories260K, 0.04% at context 64), + 640 at D = 160 (Tier A shape of D-shape-2: 542,688 -> 543,328 at context 64, 0.12%; D-shape-2 expected about 160 x 9). One program word, 256 bytes, one of the 64 table numbers.
- Rejected: the stream against the ones row (4 cycles per element more, needs max(T, D) ones); shifting E when the image is built (the output layer reads the same matrix at the unshifted scale; a second copy of E costs V D bytes).

### D-ls-cpu-20: Choosing the prompt on the board: a start-up piece in front of the unchanged program (2026-11-14)
- Decision: two build options put a start-up piece (tag `start`) at address 0; the per-token program follows it unchanged and loops to its own first address (`gen.top(b)`), so every per-token cycle number holds. (1) `prompts=[...]`: `IN`, two `SHL` (4 x SW5..0: the shifts drop SW7..6, no mask needed), a 4-byte index entry per switch number (address of the prompt, its length; all 64 entries are filled, numbers beyond the list point to prompt 0), then the prompt is copied into the prompt buffer. The table is the last region of the memory, so nothing else moves. (2) `uart_prompt=True` with the proposed `RX Rd` (op 0, fn 8): the piece writes the link to position record 0, zeroes the stop level and the filter state, sets the word state to line start, reads two bytes per token up to the byte 0xFF into the buffer (tokens beyond min(T, 255) are read and dropped, an empty prompt is ignored), and the program jumps back to it after every answer instead of HALT, after sending 0xFF. The KV cache is not cleared: a slot is written before it is read. The LFSR is not reset between answers.
- Why: copying into the existing buffer keeps one per-token program for all variants. 0xFF cannot be the first byte of a token (0x80 | (id >> 7) is at most 0x9F), so one byte ends a prompt and an answer; without an end mark the host cannot tell a full context from a slow token. In the simulator an `RX` on an empty FIFO is not executed (`waiting`), so cycle counts never include waiting.
- Numbers: stories260K shape, H = 8, G = 4, stop rule and filter on, n = tokens of the prompt, cycles per answer: table 92 + 24 n (476 at n = 16, 1,628 at n = 64), 29 words, 256 + 2 bytes per token; UART 160 + 76 n + 12 for the end mark (1,388 at n = 16, 5,036 at n = 64; 8 more per token whose id has bit 7 set), 59 words, no data. A token costs about 500,000 cycles.
- Rejected: reading the table directly on every prompt token (a second fetch path and a length compare per token); a flag byte tested on every token to run the start-up once (the start-up at address 0 costs nothing per token); both options in one program (not asked for).

### D-qat-6: The QAT learning rate is given in quantisation steps of each tensor (2026-11-14 02:20)

### D-board-2: The board model is trained on request rows and kept by the number of texts it writes exactly (2026-11-14 04:25)

### D-board-3: Exact repair of the last wrong tokens in the integer model, by integer arithmetic on E (2026-11-14 04:52)
- Decision: after QAT the board model goes through `python -m lsllm.intref.polish`. For every position of a request text where another token wins, the row of the wanted token in E is raised, and then the rows of the tokens that still win are lowered, by single codes at the coordinates where the output y of the last norm is largest at that position. A step is taken only if (a) the input embedding does not change and (b) no other position of any request text turns wrong; both are checked exactly.
- Why it is exact: a logit is `rq(y . E[v] + c_l, sh_l)`. E is also the input embedding, but the input reads `rqr(E[v], sh_e)` with `sh_e = 3` (D-arch-5): an entry of E can move up to 7 codes without changing any input. Then y is the same at every position of every text, and the new logit of token v at every position is one dot product. No gradient, no estimate, no second forward pass; the decoding rule is the CPU's (smallest index among the largest logits).
- Numbers: `runs/qat/C1` writes 258 of 284 texts exactly by the CPU rule (46 of 19,156 positions wrong). After the repair (`runs/qat/C1p`, 59 s on one core): 284 of 284, 0 positions wrong; 42 repairs, 1,421 of the 81,920 entries of E moved, no input embedding changed. Request tests in the sandbox with the integer reference: 285 of 287 pass (all 284 trained ones, and heap_sort without a text). Cost on general text: body loss 1.9411 -> 1.9543 (+0.013 nats).
- The same step on the earlier board model (`runs/qat/A2board4`, 106 texts): 86 -> 106 exact, 852 entries moved, body 1.9784 -> 1.9961.
- First version, replaced: steps chosen by |y| alone and kept only if a full re-check found no new error. It stopped at 278 of 284: the remaining repairs each broke another text. Tracking the room of every other position while choosing the steps fixed all of them.
- Limits: it repairs near-misses of a trained model; it does not teach a text (the two texts added after training stayed wrong). It needs `sh_e >= 1`. The accumulator bounds are checked again when the model is written.
- Relation to the editing sessions (D-edit-2): this is also a change of weights without gradients, but with an exact objective on training text; it is part of training the board model and is never applied to a benchmark model.

### D-asks-3: Phrases for the asks, and the conventions of the third round (2026-11-14 05:33)

### D-qat-7: The long Tier A run needed a stream-range term before it could be quantised (2026-11-14 09:10, written up 23:40)
- Decision: the Tier A benchmark model is the 30,000-step run trained on for 3,000 steps with `--stream-limit 3.5` (`runs/f/A3r`: the loss gets the mean of max(|x| - 3.5, 0)^2 over the inputs of all norms), quantised with the unchanged calibration rule and 3,000 QAT steps (`runs/qat/A3rq`).
- Why: the first quantisation of the long run (`runs/qat/A3q`) failed. Body loss 4.4487 straight after calibration, 2.1714 at the best step (1,000), then the run diverged (7.38 at the end). Cause, measured on the float model: at the input of the last norm one dimension (104) reaches 38.9, all others stay below 10.2; the earlier model's largest value there is 4.9. The stream has one scale for all sites and dimensions, taken from the 99.9th percentile of |x| (18.15 here), which gives 2 fractional bits (the earlier model: 5). Every other dimension loses three bits, and `Wo_0` uses only -8..8 of its codes.
- Tried first: more stream bits by request, letting the large dimension stop at +-127 (`--stream-bits`). After calibration only: 3 bits 2.8028, 4 bits 2.3679, 5 bits 2.2874. QAT with 4 bits at rate 0.01 (`runs/qat/A3s4`) was stable but stood at 1.968 after 2,000 steps: the float model depends on that dimension (it sets the size of the last norm, and with it how sure the model is), and QAT alone did not rebuild that.
- The range term in float: body loss 1.7170 -> 1.7248 (cost 0.008 nats); the largest value in a training batch fell from 38.9 to about 8 to 9. Calibration then gives 4 fractional bits; body 2.0828 after calibration, **1.7964 after QAT** (float 1.7248, gap 0.072). The earlier int8 model: 1.8302 (gap 0.039). The new one is better by 0.034 nats on the validation text and replaces it (the rule of D-train-3, applied to the integers as well).
- Not finished: a second QAT stage at rate 0.005 stood at 1.8007 after 2,000 of 3,000 steps when the session ended and was not repeated; finer logit codes (the model has 2 codes per nat, the earlier one 4) were not tried on this model. Both could lower the gap.
- The automatic chain had run the test sets on the failed `A3q` before the failure was noticed (greedy with filter: custom 1.0%, MBPP 0.8%, HumanEval 0.0%) and on the float model before the range term (`runs/f/A3`: custom 4.5%, MBPP 0.4%, HumanEval 0.0%; pass@10 10.0% / 1.2% / 0.6%). Those rows stay in `results/results.jsonl`. They did not choose anything: the choice between the quantisations was made on the validation text.
- Rejected: a per-dimension scale (the RMS norm mixes the dimensions, so it cannot be folded into the weights); keeping the earlier model as the final one (its float and int8 losses are both higher).
